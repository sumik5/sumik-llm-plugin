# /refactor-agent-instructions

`CLAUDE.md`・`AGENTS.md`（プロジェクト固有・グローバル・分割ルールファイルの全て）を、新しい世代のモデルに向けて再設計するコマンド。モデルの指示追従力・推論力が向上するほど、指示ファイルは「モデルが既に知っていることの説明」ではなく「そのプロジェクト固有の、コードを読んでも分からない情報」に絞るべきという考え方（コンテキストエンジニアリング）に基づく。

## 概要

| 項目 | 内容 |
|------|------|
| 対象ファイル | プロジェクト `CLAUDE.md` / `AGENTS.md`、グローバル `~/.claude/CLAUDE.md` / `~/.codex/AGENTS.md`、CLAUDE.md が参照する分割ルールファイル（例: `rules/*.md`） |
| 診断観点 | 6カテゴリ（下記 Step 2） |
| 出力形式 | カテゴリ別の diff（該当箇所引用＋問題点＋提案＋理由）を提示 → `AskUserQuestion` で承認 → 適用 |
| `--check` | 診断結果のみ報告し、ファイルは一切変更しない |
| `--project-only` / `--global-only` | 対象範囲を限定する |
| 前提 | 本コマンドは既存記述の整理・再配置に特化する。新規の学び・訂正の記録は `capturing-learnings`、その恒久化・昇格判断は `consume-learnings` が担当する（本コマンドでは行わない） |

---

## Step 1: 対象ファイルの検出

`$ARGUMENTS` にパス指定があればそれを対象にする。指定がなければ以下を自動検出する。

```bash
# プロジェクト側
/usr/bin/find . -maxdepth 2 \( -name "CLAUDE.md" -o -name "AGENTS.md" \) 2>/dev/null
# CLAUDE.md が @path/to/file.md 形式で参照している分割ファイルを抽出
/usr/bin/grep -oE "^@[^ ]+\.md" CLAUDE.md 2>/dev/null

# グローバル側（--project-only 指定時はスキップ）
ls -la ~/.claude/CLAUDE.md ~/.codex/AGENTS.md 2>/dev/null
```

- 複数ファイルが見つかった場合（プロジェクト固有＋グローバル＋分割ルール）は、`AskUserQuestion` で対象範囲（全部 / プロジェクトのみ / グローバルのみ / 個別選択）を確認する。
- 🔴 グローバル側はユーザーの dotfiles 実体への symlink であることが多い。`readlink -f <path>` で実体パスを解決してから読み書きする。特に `~/.codex/AGENTS.md` は多くの環境で `~/dotfiles/codex/AGENTS.md` 等が実体であり、symlink 先ではなく symlink 自体を編集すると変更が反映されない。
- 分割ルールファイル（`rules/*.md` 等）が見つかった場合、それらも診断対象に含める（CLAUDE.md 本体だけを軽量化しても分割先が肥大化していれば意味がない）。

---

## Step 2: 6カテゴリ診断

各ファイルの全文を読み、以下の6カテゴリで問題箇所を洗い出す。

| # | カテゴリ | 検出パターン | 該当の具体例 | 対応方針 |
|---|---------|-------------|-------------|---------|
| A | コード可読情報の重複記述 | 命名規則・ディレクトリ構成・技術スタック等、リポジトリを読めば分かる情報 | 「`src/components/` にReactコンポーネントを置く」等の自明な構造説明 | 削除（コードが唯一の正とする） |
| B | 陳腐化する動的情報の混在 | 完了済みタスク・進捗状況・特定日付の作業ログ・「〜を修正した」等の過去形メモ | 「2026-05にX機能を実装済み」等、時間とともに真偽が変わる記述 | 削除 or Issue/タスク管理・日付付きメモリファイルへ移動 |
| C | 一般的原則の記述 | モデルが訓練時点で既に知っている一般的なプログラミング原則・フレームワーク解説 | 「SOLID原則とは〜」「関数は小さく保つ」等の教科書的説明 | 削除（モデルの既知知識に委ねる） |
| D | 特定場面専用手順の未分離 | 特定のタスク（デプロイ・検証・移行等）でのみ使う長い手順が常時読み込み位置にある | 詳細な検証コマンド列やチェックリストが CLAUDE.md 本体に直書きされている | 別ファイル（Skill / `docs/` 配下）へ分離し、「〇〇時は `docs/xxx.md` を参照」という条件付き参照に置き換える（Progressive Disclosure） |
| E | 禁止表現の偏重 | 「〜してはいけない」「禁止」等、代替手段を伴わない否定形の指示が多い | 「マイグレーションを自動実行してはいけない」（代替不明） | 代替手段を明示する肯定形へ書き換える（例: 「本番データ変更は承認つき専用ジョブで実施する」） |
| F | 他ファイルとの指示重複 | CLAUDE.md・Skill・ツール説明（Agent定義等）で同一趣旨の指示が繰り返されている | 同じコーディング規約がCLAUDE.mdとSkill両方に書かれている | 一元化先を1つ決め、他方は参照のみに変更する |

診断は指摘のたびに「該当ファイル:該当行」を明記し、後続の diff 提示で引用できるようにする。

---

## Step 3: 改善提案の生成（diff形式）

カテゴリごとに以下の形式で提案をまとめる。

```markdown
### [カテゴリ] 該当ファイル:行番号

**該当箇所（引用）**:
> （原文の該当行）

**問題点**: （カテゴリ表の理由に沿って具体的に）

**提案**:
- 削除する場合: 「削除する（理由: ...）」
- 移動する場合: 「〇〇へ移動する（移動先が存在しなければ新規作成する）」
- 書き換える場合: 変更前後を対比で示す
  - 変更前: `...`
  - 変更後: `...`
```

`--check` 指定時はここで提案一覧を提示して終了する（ファイルは変更しない）。

---

## Step 4: ユーザー承認

`AskUserQuestion` で適用範囲を確認する。

- 全提案を適用する
- カテゴリ単位で選択する（例: E（禁止表現書き換え）のみ適用）
- 個別の提案ごとに選択する
- 適用しない（診断結果のみで終了）

---

## Step 5: 適用

- **削除**: 該当箇所を除去する。
- **移動**: 移動先ファイルが存在しなければ新規作成する。
  - Skill が使えるプロジェクトなら該当 Skill の `references/` 等
  - Skill を持たないプロジェクトなら `docs/` 配下、または日付付きメモリファイル
  - 進捗・作業ログは Issue・タスク管理ツールへの移行を提案し、ファイルには残さない
- **書き換え**: 禁止表現→代替手段付き表現、一般原則の説明→モデルの判断力に委ねる簡潔な参照に置き換える。
- **Progressive Disclosure化**: 常時読み込み本文の中に「〇〇する時は `path/to/doc.md` を読む」という条件付き参照を追加し、詳細本体は分離先ファイルへ移す。

適用後、変更差分は必ず `git diff` で確認できる状態にする（コミットは本コマンドの責務外。対象プロジェクトの慣習に従いユーザー自身が行う）。

---

## Step 6: 検証・報告

以下を表形式で報告する。

- 変更ファイル一覧と行数・文字数の削減率
- カテゴリ別の適用件数（削除 / 移動 / 書き換え / 見送り）
- Progressive Disclosure化により新設・更新した参照先ファイル一覧
- ロールバック手順（`git diff` で変更点を確認 → 不採用なら `git checkout -- <file>` で元に戻せる旨）

変更後の効果は静的検証だけでは確認できないため、「次の数タスクの実行で、見落とし・意図しない禁止行動の増加が起きていないか様子を見てください」と案内して終える。

## 注意点

| If X | then Y |
|------|--------|
| 対象がグローバル設定ファイル（symlink）の場合 | `readlink -f` で実体を解決してから編集する。symlink 自体を書き換えても反映されないことがある |
| 対象が sumik-claude-plugin リポジトリ自身の CLAUDE.md / rules 配下の場合 | このリポジトリの絶対ルール（書籍名・著者名・出版社名の禁止等）を遵守しつつ整理する。本コマンド自体が新規コンポーネントを追加するわけではないため、`plugin.json` の version bump は不要 |
| カテゴリEの書き換えで代替手段が思いつかない場合 | 無理に肯定形へ書き換えず、禁止理由（何が壊れるか）を一言添えるだけでも改善とする |
| 診断対象に「踏むと壊れる罠」「意図的に採用しなかった設計判断」に類する記述がある場合 | これらは陳腐化しにくく再発防止価値が高いため、カテゴリB/Cの削除対象からは除外する |
| ユーザーが個別提案の採否を保留したい場合 | Step 4 で該当提案のみ「適用しない」を選び、他の提案は先に進めてよい |
| カテゴリDで新規に外部ファイルを作成する前 | `git check-ignore -v <path>` 等で対象ディレクトリが gitignore 対象でないか確認する。`docs/**` のような広い ignore パターンがあるリポジトリでは、そのディレクトリが「一時作業ディレクトリ」用途である可能性を疑い、恒久ドキュメントの置き場としないこと |
| カテゴリDで移動先を決める前 | 関連する既存スキル（プロジェクト内に管理用スキル〈例: authoring-plugins〉があれば優先）の `references/` 配下を検索し、同種の一次情報源が既に存在しないか確認する。既にあれば孤立した新規ファイルを作らず、そちらへ実例として統合するほうが発見性・保守性が高い |
