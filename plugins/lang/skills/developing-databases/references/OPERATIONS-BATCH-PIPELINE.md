# 分析システムのバッチ処理運用パターン

分析システム（データウェアハウス・データマート・BIバックエンド等）では、業務システムから収集したデータを定期的に加工し、参照系が読みやすい形へ変換するバッチ処理が中核を担う。本ファイルはこのバッチ処理を「ジョブフロー設計」「テーブル運用」「更新方式」「テスト」「運用チェック」という5つの観点から扱う。個別のSQL構文（JOIN・ウィンドウ関数・集合演算等）は他ファイルに譲り、ここでは**運用パターンとしての判断基準**に絞る。

---

## 1. バッチ処理の位置づけ

分析システムは大きく「オンライン処理（参照系がリアルタイムに読むレイヤー）」と「バッチ処理（データを定期的に加工するレイヤー）」の2層で構成される。両者は責務が異なる。

| 観点 | オンライン処理 | バッチ処理 |
|------|--------------|-----------|
| 実行タイミング | ユーザーのリクエスト時 | スケジュール（日次・時間次等） |
| 処理対象 | 少量（1リクエスト分） | 大量（対象期間全体） |
| 求められる特性 | 低レイテンシ | 高スループット・再実行安全性 |
| 失敗時の扱い | リトライはクライアント側の責務 | ジョブスケジューラによる自動リトライ・アラート |

バッチ処理は「ソースシステムからデータを抽出し、変換し、分析用の形式でロードする」という一連の流れを担う（`INTERNALS-MODELS.md`のディメンショナルモデルにおけるETLプロセスの言及も参照）。本ファイルはこの ETL のうち、実際にジョブをどう設計し、テーブルをどう運用し、更新をどう安全に行うかという実務レベルの判断基準を扱う。

## 2. ジョブフロー設計

### 2.1 ジョブの粒度分割

1つのバッチジョブに複数の責務を詰め込むと、失敗時の影響範囲が広がり、再実行のコストも増大する。**1ジョブ1責務**を原則とし、以下を粒度分割の判断材料にする。

| 判断基準 | 分割を検討する条件 |
|---------|------------------|
| 再実行単位 | ある処理だけが失敗した際、他の処理を再実行せずに済ませたい |
| 実行時間 | 単一ジョブの実行時間が許容SLAを超える見込みがある |
| 依存先の障害影響 | 特定の外部データソースの遅延が他の処理をブロックしてはならない |
| 監視の粒度 | 「どの処理が失敗したか」をアラートで即座に特定したい |

粒度を細かくしすぎるとジョブ間の依存関係管理コストが増えるため、「独立して再実行する意味があるか」を分割基準にする。

### 2.2 依存関係管理

複数ジョブが存在する場合、実行順序の制約（DAG: 有向非巡回グラフ）を明示的に管理する必要がある。

| 依存パターン | 例 | 実行方式 |
|------------|---|---------|
| 直列依存 | ワークテーブル生成 → サマリーテーブル集計 | 前段の成功を確認してから次段を起動 |
| 並列実行可能 | 独立した複数ソースからの取り込み | 同時実行し、全完了を待ってから後続を起動 |
| 部分的依存 | 複数の集計ジョブが共通のワークテーブルにのみ依存 | 共通の前段完了後、後続群を並列起動 |

依存関係はジョブスケジューラ（DAGベースのワークフローエンジン等）で明示的に定義し、SQLスクリプト内のコメントだけに頼らないようにする。依存が暗黙的（「このジョブは手動でXの後に実行する」等）だと、担当者交代時に実行順序の知識が失われる。

```
# DAG定義の骨子（ワークフローエンジンの疑似記法）
extract_orders ─┐
                ├─▶ build_work_sales ─▶ build_summary_sales ─▶ notify_success
extract_returns ┘

# extract_orders と extract_returns は独立ソースのため並列実行
# build_work_sales はその両方の完了を待って起動（依存の合流点）
```

このように依存関係を宣言的に記述しておけば、あるジョブが失敗した際に「どこまで巻き戻して再実行すべきか」をDAGから機械的に判定できる。巻き戻し範囲の判断は6章の運用チェックリストでも再確認する。

### 2.3 中間データの受け渡し方式

ジョブ間でデータを受け渡す方式には複数の選択肢があり、それぞれ運用上のトレードオフがある。

| 方式 | 特徴 | 適した場面 |
|------|------|-----------|
| テーブル経由 | SQLで完結、他ジョブからも参照可能 | 同一DB内で完結する処理 |
| ファイル経由（CSV/Parquet等） | DB外のツールとも連携しやすい | 異なるシステム間でのデータ交換 |
| メッセージキュー経由 | イベント駆動での連携が可能 | リアルタイム性が求められる部分連携 |

本ファイルは主に「テーブル経由」の受け渡し、すなわち次章の**ワークテーブル**を扱う。

## 3. ワークテーブルとサマリーテーブル

分析バッチでは、最終成果物であるサマリーテーブルに至るまでの中間生成物を保持する場所が必要になる。この役割を担うのがワークテーブルである。

### 3.1 ワークテーブル

ワークテーブルは、ジョブの実行過程で一時的に使われる中間テーブルである。

- **ライフサイクル**: ジョブの実行中のみ存在意義を持つ。ジョブ完了後に切り捨て（`TRUNCATE`）るか、次回実行時に上書きされる前提で設計する
- **スキーマ分離**: 本番の参照系スキーマとは別のスキーマ（例: `work`, `staging`）に置き、参照系のクエリから誤って参照されないようにする
- **命名規約**: ジョブ名やステップ番号を含めた命名（例: `work_sales_step1_dedup`）にし、どのジョブが生成したか一目でわかるようにする

```sql
-- ワークテーブルの典型的な使い回しパターン（実行のたびに内容を洗い替え）
TRUNCATE TABLE work.sales_step1_dedup;

INSERT INTO work.sales_step1_dedup
SELECT order_id, customer_id, amount, ordered_at
FROM staging.raw_orders
WHERE ordered_at >= :batch_date AND ordered_at < :batch_date + INTERVAL '1' DAY;
-- :batch_date はジョブ実行時に外部から注入するパラメータ（4.1参照。CURRENT_DATEの直書きは避ける）
```

### 3.2 サマリーテーブル

サマリーテーブルは、集計・変換が完了した最終成果物であり、参照系（BIツール・アプリケーション）が直接読みに行く対象である。

- **ライフサイクル**: 恒久的に存在し、次回バッチ実行まで内容が保持される
- **参照要件**: 参照系から常時読み取り可能でなければならず、更新中に参照不能になる時間帯を作らないよう設計する（詳細は4章）
- **再作成コスト**: サマリーテーブルは通常ワークテーブルより行数が少ない（集計後のため）が、参照系の可用性要件が絡むため更新方式の選択がより重要になる

### 3.3 使い分け判断表

| 軸 | ワークテーブル | サマリーテーブル |
|----|--------------|-----------------|
| ライフサイクル | ジョブ実行中のみ一時的 | 恒久的（次回バッチまで） |
| 参照元 | 同一バッチ内の後続ステップのみ | BIツール・アプリケーション等の参照系全般 |
| 再作成コスト | 頻繁に作り直す前提（許容） | 参照不能な時間を避ける設計が必須 |
| スキーマ配置 | 分離されたワーク用スキーマ | 参照系が閲覧可能な本番スキーマ |

## 4. データ更新の2方式

サマリーテーブルの内容を最新化する方式には、大きく分けて「差分更新」と「全行洗い替え」の2つがある。

### 4.1 差分更新

対象期間（例: 前日分）のデータのみを追加・更新する方式。

- **対象期間のパラメータ化**: バッチ実行日を`CURRENT_DATE`のようにSQL内で直接評価してはならない。実行日をジョブのパラメータとして外部から渡し、SQL側では変数として参照する。これにより、任意の過去日を指定した再実行（リカバリ）が可能になる
- **冪等性の確保**: 「同じパラメータで再実行しても結果が変わらない」ことを設計の中心に置く。単純な`INSERT`の繰り返しだけでは再実行のたびに行が増える（二重登録）ため、以下のいずれかで対処する

  | 対処法 | 内容 |
  |--------|------|
  | 事前削除 | 対象期間の既存データを`DELETE`してから`INSERT`する |
  | UPSERT | 主キー衝突時は更新する（`INSERT ... ON CONFLICT DO UPDATE`等、方言差あり） |
  | 洗い替え | 対象期間分のワークテーブルを作り直し、サマリーテーブルの該当パーティションを入れ替える |

- **二重登録の防止**: ジョブの多重起動（スケジューラの設定ミス・手動実行との重複等）に備え、実行中フラグや排他制御の仕組みをジョブ管理層に持たせる。SQLの冪等性だけでは同時実行の防止まではカバーできない

```sql
-- 事前削除方式（同一パラメータでの再実行に対して安全）
DELETE FROM sales_summary
WHERE sales_date = :batch_date;

INSERT INTO sales_summary (sales_date, product_id, total_amount)
SELECT :batch_date, product_id, SUM(amount)
FROM work.sales_step1_dedup
GROUP BY product_id;

-- UPSERT方式（DELETEを伴わず主キー単位で更新、方言はDBMSごとに異なる）
INSERT INTO sales_summary (sales_date, product_id, total_amount)
SELECT :batch_date, product_id, SUM(amount)
FROM work.sales_step1_dedup
GROUP BY product_id
ON CONFLICT (sales_date, product_id)
DO UPDATE SET total_amount = EXCLUDED.total_amount;
```

どちらの方式も、`:batch_date`という同一パラメータで2回実行した結果が1回実行した結果と一致することが冪等性の判定基準になる（5.3のテストデータ準備方針で実際に検証する）。

### 4.2 全行洗い替え

テーブルの内容全体を毎回作り直す方式。差分更新の複雑さ（冪等性設計・UPSERT）を避けられる代わりに、対象データ量が大きいほど処理コストが増す。

全行洗い替えには実装方式が2つあり、**アトミック性**（参照系から見た切り替えの一貫性）に明確な違いがある。

| 方式 | 手順 | アトミック性 |
|------|------|-------------|
| `DROP` → `CREATE` 方式 | 既存テーブルを`DROP`し、同名で`CREATE`し直してデータを投入する | ❌ 再作成中はテーブルが存在せず、参照系から見て**参照不能な時間帯**が生じる |
| `CREATE` → 入れ替え方式 | 新テーブルを別名（例: `sales_summary_new`）で作成・データ投入した後、`RENAME`で本番名と入れ替える | ✅ リネームは多くのDBMSで単一のメタデータ操作として扱われ、切り替えが**原子的**に完了する。参照系が「古い内容」と「新しい内容」のどちらかしか見ない |

```sql
-- 入れ替え方式の骨子（DBMSによりRENAME構文は異なる）
CREATE TABLE sales_summary_new AS
SELECT ... FROM work_sales_aggregated;

-- ここまでの間、参照系は引き続き旧 sales_summary を読める

ALTER TABLE sales_summary RENAME TO sales_summary_old;
ALTER TABLE sales_summary_new RENAME TO sales_summary;
-- 2行のRENAMEも、DBMSによってはトランザクションで囲み単一操作として扱う
DROP TABLE sales_summary_old;
```

`DROP` → `CREATE` 方式は実装がシンプルだが、再作成に時間がかかるテーブルほど参照不能な窓が長くなる点に注意する。参照系の可用性要件が緩い（夜間バッチのみで日中の参照がない等）場合を除き、入れ替え方式を優先する。

### 4.3 方式選択の判断表

| 軸 | 差分更新推奨 | 全行洗い替え推奨 |
|----|------------|-----------------|
| データ量 | 大規模（全件再計算が高コスト） | 小〜中規模（全件再計算が現実的な時間で終わる） |
| 更新頻度 | 高頻度（時間次等） | 低頻度（日次・週次等） |
| 参照要件 | 常時参照可能である必要がある | 短時間の切り替えが許容される、または入れ替え方式を併用 |
| 再実行コスト | 対象期間のみの再計算で済む設計が可能 | 常に全件を再計算するため再実行コストは一定 |
| 実装の複雑さ | 冪等性設計・UPSERTの実装が必要 | シンプル（入れ替え方式でもRENAMEのみ） |

迷った場合は、まず全行洗い替え（入れ替え方式）から始め、データ量の増大に伴って処理時間がSLAを超えるようになった段階で差分更新への移行を検討するのが現実的な進め方である。

## 5. SQLジョブのテスト方針

### 5.1 テーブル名の変数化

本番環境とテスト環境で同一のSQLロジックを使い回すため、テーブル名をSQL内にハードコードせず、実行時にパラメータとして注入できるようにする（テンプレートエンジン・スキーマ切り替え・環境変数展開等、手段は問わない）。これにより、テスト環境の隔離されたテーブルに対して本番と同一のSQLを実行し、結果を検証できる。

### 5.2 EXCEPT演算子によるデータ突き合わせテスト

SQLジョブの出力が「期待される結果と一致するか」を検証する最も確実な方法は、**双方向の差分を取り、両方向とも空集合であることを確認する**ことである。

```sql
-- 実際の出力と期待結果の突き合わせ（双方向）
-- 1. 実際の出力にあって期待結果にない行（余分な行）
SELECT * FROM actual_output
EXCEPT
SELECT * FROM expected_result;

-- 2. 期待結果にあって実際の出力にない行（不足している行）
SELECT * FROM expected_result
EXCEPT
SELECT * FROM actual_output;
```

**片方向だけの確認では不十分**な点に注意する。1.のクエリのみを確認して「空だったので一致した」と判断すると、期待結果側にしかない行（欠落）を見逃す。逆に2.のみでは余分な行を見逃す。両方向がともに空集合であって初めて、2つの結果セットが集合として一致すると言える。

`EXCEPT`が未実装のDBMSでは代替手段が必要になる。集合演算子の実装差やエミュレーション方法（`NOT IN`による代替等）、および集合の相等性チェックの一般公式は `lang:writing-effective-sql` の `SET-OPERATIONS-AND-QUANTIFICATION.md` を参照。

### 5.3 テストデータの準備方針

| 方針 | 内容 |
|------|------|
| 境界値の網羅 | NULL混入行、空文字列、対象期間の境界日（前日終端・当日開始等）を含める |
| 冪等性の検証 | 同一パラメータでジョブを2回連続実行し、2回目の結果が1回目と一致することを確認する |
| 小規模データでの高速反復 | 本番相当の大量データではなく、代表的なパターンを網羅した小規模データセットでジョブロジックを検証し、性能検証は別途大規模データで行う |

```sql
-- 冪等性検証の骨子: 同一パラメータで2回実行した結果セットが一致するかを
-- 5.2のEXCEPT突き合わせでそのまま確認できる
-- 1回目実行後のスナップショットを退避
CREATE TABLE test.sales_summary_run1 AS SELECT * FROM sales_summary WHERE sales_date = :batch_date;

-- 同一パラメータでジョブを再実行した後、2回目の結果と比較
SELECT * FROM sales_summary WHERE sales_date = :batch_date
EXCEPT
SELECT * FROM test.sales_summary_run1;
-- 空集合であれば、1回目と2回目の実行結果が完全に一致=冪等
```

## 6. 運用チェックリスト

バッチジョブを本番投入する前に、以下を確認する。

| チェック項目 | 確認内容 |
|------------|---------|
| 再実行安全性 | ジョブが失敗した状態から、同じ手順で安全に再実行できるか |
| 冪等性 | 同一パラメータでの複数回実行が同じ結果になるか（4.1参照） |
| 依存ジョブの再実行範囲 | あるジョブを再実行する際、後続の依存ジョブも連鎖的に再実行が必要か、その範囲は明確か |
| 失敗時のリカバリ手順 | 途中で失敗した場合、どこから再開すべきかが手順として明文化されているか |
| 参照系への影響 | 更新中に参照系が不整合なデータを読まないか（4.2のアトミック性を参照） |
| 監視・アラート | ジョブの失敗・遅延がわかる仕組みがあるか（2.1の粒度分割が監視粒度と対応しているか） |

これらの項目は、2〜5章で述べた設計判断（ジョブ粒度・更新方式・テスト方針）が実際に運用可能な形になっているかを最終確認するためのものであり、いずれか1つでも欠けると障害発生時の復旧が困難になる。
