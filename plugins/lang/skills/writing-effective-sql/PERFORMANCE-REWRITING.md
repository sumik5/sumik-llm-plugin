# 実行計画とパフォーマンスリライト

SQLは「何を取得したいか（What）」を宣言するだけで、「どうやって取得するか（How）」の手続きはDBMS側のオプティマイザに委譲されています。この権限委譲のおかげで生産性は上がりましたが、代償として、パフォーマンスに問題が起きたときにHowを覗き見る必要が生じます。この文書では、実行計画を読んでボトルネックを特定する方法と、クエリの書き方を変えるだけで速くできる技法（遅い→速い書換カタログ）を扱います。

## この文書の範囲

| 扱う内容 | 扱わない内容（委譲先） |
|---------|----------------------|
| 実行計画の読み方・活用 | バッファ管理・ストレージエンジンの内部構造 → `lang:developing-databases` |
| インデックスが効くクエリの書き方（SARGable条件） | インデックスの物理設計・作成そのもの（列順序・複合インデックス設計） → `lang:developing-databases` |
| クエリの書き換えによる高速化 | 正規化・非正規化などのスキーマ変更 → `lang:developing-databases` |
| 標準SQLレベルの書換パターン | DBMSごとのチューニングパラメータ・統計情報収集コマンドの詳細 → 各DBMSのマニュアル |

判断に迷ったら「クエリの書き方だけで対処できるか」「テーブル定義やインデックス構成を変える必要があるか」で線を引いてください。後者に該当する場合は後述の AskUserQuestion 指針に従います。

## 実行計画の読み方

### クエリがデータアクセスに変換されるまで

SQL文を受け取ってから実際のデータアクセスが行われるまで、DBMSの内部では次のモジュールが順に処理を行います。

| モジュール | 役割 |
|-----------|------|
| パーサ（parser） | SQL文の構文解析。構文エラーの検出とDBMS内部形式への変換 |
| オプティマイザ（optimizer） | 選択可能な実行計画を複数生成し、コストを計算して最も低コストな1つに絞り込む |
| カタログマネージャ（catalog manager） | テーブル・インデックスの統計情報（レコード数、カーディナリティ、ヒストグラム等）をオプティマイザに提供 |
| プラン評価（plan evaluation） | オプティマイザが立てた複数の実行計画から最終的な1つを選択し、手続き型コードに変換して実行 |

実行計画はDBMSがそのまま実行するコードではなく、人間が読める「計画書」です。パフォーマンスが悪いSQL文は、この計画書を読むことで改善の糸口を見つけられます。

### 統計情報が実行計画の質を決める

オプティマイザは実テーブルを見ず、カタログに記録された統計情報（レコード数・列のカーディナリティ・NULLの数など）だけを頼りに実行計画を組み立てます。テーブルへの大量の挿入・更新・削除が行われたのに統計情報が更新されていないと、オプティマイザは古い前提のまま非効率な実行計画を選びます。

| 症状 | 原因の疑い | 対処 |
|------|-----------|------|
| データ量が大きく変わったのに実行計画が変化しない | 統計情報が古い | 統計情報の手動更新、または大量更新バッチへの統計情報更新ジョブの組み込み |
| テーブルを空にしても実行計画のRows数が変わらない | 統計情報がメタ情報止まりで実テーブルを見ていない（想定どおりの挙動） | 統計情報を再取得すれば反映される |

具体的な統計情報更新コマンドはDBMSごとに異なるため、対象DBMSが不明な場合はSKILL.mdの指針に従いAskUserQuestionで確認してください。

### EXPLAINで確認すべき3項目

DBMSが異なっても、実行計画の出力に共通して現れる重要な項目は次の3つです。

1. **操作対象のオブジェクト** — どのテーブル・インデックスに対する操作か
2. **オブジェクトに対する操作の種類** — フルスキャンかインデックススキャンか、どの結合アルゴリズムか
3. **操作の対象となるレコード数** — 各操作で何行処理されるか（統計情報由来の推定値であり実測値ではないことに注意）

`Cost`（実行コスト）は相対評価の目安に過ぎず、絶対値から実行時間を推測することはできません。実際の処理時間・処理行数を取得する機能を持つDBMSもあるので、正確な計測が必要な場合はDBMSごとの実測系機能（例: 実行計画のプロファイリング機能）を利用してください。

### テーブルフルスキャンとインデックススキャンの読み分け

WHERE句のない単純なSELECTと、主キー検索を付けたSELECTの実行計画を比較すると、次のような違いが現れます。

```sql
-- フルスキャンになるクエリ
SELECT * FROM Shops;
```

```
Seq Scan on shops (cost=0.00..1.60 rows=60 width=22)
```

```sql
-- インデックススキャンになるクエリ
SELECT * FROM Shops WHERE shop_id = '00050';
```

```
Index Scan using pk_shops on shops (cost=0.00..8.27 rows=1 width=320)
  Filter: (shop_id = '00050'::bpchar)
```

「Seq Scan」「Index Scan」（DBMSによっては「TABLE ACCESS FULL」「INDEX UNIQUE SCAN」等の表記）が2つ目の項目＝操作の種類です。フルスキャンはデータ量に比例してコストが増大するのに対し、B-treeインデックスによるスキャンはデータ量に対して対数的にしかコストが増えないため、データ量がある損益分岐点を超えるとインデックススキャンが有利になります。ただし、テーブルが小さい場合はフルスキャンとインデックススキャンの差はほとんど出ません。

### 結合の実行計画: 3つのアルゴリズム

結合を含むSQLが遅いケースは非常に多く、実行計画も複雑になりがちです。DBMSが選択する結合アルゴリズムは主に3種類あります。

| アルゴリズム | 動作概要 | インデックスの要否 | 有利な条件 |
|------------|---------|-------------------|-----------|
| Nested Loop | 片方のテーブルの1行ごとに、結合条件に合致する行をもう一方のテーブルから探す（二重ループ） | 結合対象列にインデックスがあると高速 | 駆動表（先にアクセスされる側）の結果セットが小さい |
| Sort Merge | 両テーブルを結合キーでソートしてから順次結合する | 結合順序自体はインデックスと無関係だが、ソート済みインデックスがあればソートを省略できる | 両者を効率的にソートできる場合。両側のソートコストが高いため実際にはあまり選ばれない |
| Hash | 片方のテーブルからハッシュテーブルを作り、もう一方の行を照合する | 結合対象列そのものにはインデックス不要。WHERE述語やON述語側の列インデックスは効果あり | ハッシュテーブルが十分小さく作れる場合 |

実行計画は一般にツリー構造で出力され、**入れ子の深い操作ほど先に実行されます**。同じ階層で上に記述されているテーブルが先にアクセスされる「駆動表（driving table）」です。結合が絡む実行計画を読むときは、まずどちらが駆動表かを確認してください。

### オプティマイザで解決しない場合の最終手段

統計情報を最新化し、SARGable条件（後述）に書き換えても改善しない場合、DBMSによってはヒント句でオプティマイザに実行計画を強制変更できます。ただしヒント句はDBMSの拡張機能であり標準SQLではなく、オプティマイザの判断ミスを個別にねじ伏せる最終手段です。まずは統計情報の更新とクエリの書き換えを優先し、それでも解決しない場合にのみ検討してください。

## SARGable条件でインデックスを活かす

### SARGableとは

SARGable（Search ARGument ABLE）とは、WHERE句の条件がインデックスによる絞り込みに利用できる形になっていることを指します。インデックスを作成していても、WHERE句の書き方次第でそのインデックスが一切使われずフルスキャンになってしまうことがあります。

### インデックスが機能しない書き方カタログ

以下はいずれも「選択率が良い（絞り込みが効く）条件であるにもかかわらず、書き方のせいでインデックスが使えない」典型パターンです。

| NGパターン | 例 | なぜ使えないか | 書き換え |
|-----------|-----|---------------|---------|
| 索引列で演算・関数を使用 | `WHERE col_1 * 1.1 > 100` | インデックスに格納されているのは`col_1`の値そのものであり、演算結果ではないため | `WHERE col_1 > 100 / 1.1`（演算を右辺に寄せる） |
| 索引列に関数を適用 | `WHERE LENGTH(col_1) = 10` | 関数を全行に適用しなければ判定できずテーブルスキャンになる | 可能なら関数を使わない条件に言い換える。DBMSが関数ベースインデックスをサポートしていれば別インデックスで対処（設計判断のため`lang:developing-databases`領域） |
| `IS NULL` / `IS NOT NULL` | `WHERE col_1 IS NULL` | インデックス内部に原則としてNULLが格納されないため | 代替不要な限り無理に書き換えない。`IS NOT NULL`をどうしても高速化したいなら最小値未満との不等号比較で代用する手もあるが可読性を犠牲にするため常用は避ける |
| 否定形 | `WHERE col_1 <> 100` / `!=` / `NOT IN` | 「一致しない」ことの証明にはほぼ全行の確認が必要なため | 可能なら肯定形（`IN`・範囲指定等）に言い換える。困難な場合は許容する |
| 中間一致・後方一致のLIKE | `WHERE col_1 LIKE '%abc%'` / `LIKE '%abc'` | B-treeインデックスは前方一致にしか使えない | 前方一致（`LIKE 'abc%'`）に変更できないか要件を確認する。全文検索が必要な場合は専用のインデックス機構を検討（`lang:developing-databases`領域） |
| 暗黙の型変換 | 文字列列に対し `WHERE col_1 = 10`（列は文字列型） | DBMSが値を変換してから比較するため列側に暗黙変換がかかりインデックスが無効化される | `WHERE col_1 = '10'`のように条件値側を明示的に変換する（列側を変換しない） |
| OR条件 | `WHERE col_1 > 100 OR col_2 = 'abc'` | 複数列にまたがるOR条件は複合インデックスでは効率的に扱えない | 分離可能なら`UNION`（または`UNION ALL`）に書き換える |

判断基準テーブル:

| 状況 | 対処 |
|------|------|
| 索引列に演算・関数が付いている | 右辺（条件値側）に計算を寄せられないか検討する（最優先） |
| 否定形・中間一致LIKEがどうしても必要 | 書き換えでは解決しないため許容する。頻出するなら専用インデックス機構の採用を`lang:developing-databases`で検討 |
| 型が食い違っている | 条件値を列の型に明示的にキャストする。列側のキャストは絶対に避ける |

### 選択率が高い場合はインデックスが逆効果になる

SARGableな書き方をしていても、条件がテーブルの大部分にヒットする（選択率が高い）場合はインデックススキャンよりフルスキャンの方が速いことがあります。目安として、絞り込み後の行数がテーブル全体の5〜10%を下回るかどうかが分岐点になることが多いですが、正確な閾値はDBMSやストレージ性能に依存します。

特に注意が必要なのは、**同じ構文でもパラメータの値によって選択率が変動する**ケースです。

```sql
SELECT order_id
  FROM Orders
 WHERE receive_date BETWEEN :start_date AND :end_date;
```

`:start_date`と`:end_date`に同一日を渡せば選択率は低くインデックスが有利ですが、1年分の範囲を渡せば選択率が跳ね上がりフルスキャンの方が有利になることがあります。この種のクエリはオプティマイザがバインド変数の実値ごとに最適なプランを選べるとは限らないため、パラメータの分布に偏りがある場合はDBMSごとの対処（バインド変数ピーキング等）が必要になることがあります。列名に`_flg`や`_status`が付くような値の種類が少ない列も、同様の理由でインデックスが効きにくい代表例です。

| いつインデックスを疑うべきか | いつフルスキャンを許容してよいか |
|---------------------------|------------------------------|
| WHERE句に絞り込み条件が全く無いバッチ処理 | オンライン処理ではなくバッチ処理で、そもそも全件処理が目的の場合 |
| 選択率がパラメータ依存で変動する検索画面 | 対象テーブルが小さくメモリに収まる規模の場合 |

## 遅い→速い書換カタログ

以下はいずれも標準SQLレベルで同じ結果を返すが実行効率が異なる書き方のペアです。DBMSやバージョンによる実装差はありますが、まず疑うべき定石として押さえてください。

### IN（サブクエリ）→ EXISTS / JOIN

```sql
-- 遅い: サブクエリの結果を一時的なワークテーブルに展開してから全件走査する
SELECT * FROM Class_A
 WHERE id IN (SELECT id FROM Class_B);

-- 速い: 結合キーにインデックスがあればインデックス参照のみで済み、1行見つかった時点で打ち切れる
SELECT * FROM Class_A A
 WHERE EXISTS (SELECT * FROM Class_B B WHERE A.id = B.id);

-- 同じ意図をJOINで表現する（ワークテーブルも作られない）
SELECT A.id, A.name
  FROM Class_A A INNER JOIN Class_B B ON A.id = B.id;
```

EXISTSが速いと期待できる理由は2つあります。①結合キーにインデックスがあれば実表を見にいかずインデックス参照だけで済む。②条件に合致する行を1件見つけた時点で検索を打ち切れる（NOT EXISTSでも同様）。

| いつ使う | いつ使わない |
|---------|-------------|
| サブクエリを引数に取るIN/NOT INがボトルネックになっている | INの引数が固定値リスト（`IN (1, 2, 3)`等）の場合はそもそも問題になりにくい |
| NOT INとNOT EXISTSで結果が一致することを確認できている（NULL混入時は非同値になるため要注意。詳細はFOUNDATIONS-AND-NULL.md参照） | INのままで十分な応答時間が出ており可読性を優先したい場合 |

最近のDBMSはIN述語自体の最適化も進んでいるため、将来的にはこの書換の効果が縮小していく可能性がありますが、現時点では依然として有効な定石です。

### DISTINCTの重複排除をEXISTSで代用する

```sql
-- 遅い: 結合結果の重複をDISTINCTのソートで排除する
SELECT DISTINCT I.item_no
  FROM Items I INNER JOIN SalesHistory SH ON I.item_no = SH.item_no;

-- 速い: そもそも重複を発生させない
SELECT item_no
  FROM Items I
 WHERE EXISTS (SELECT * FROM SalesHistory SH WHERE I.item_no = SH.item_no);
```

一対多の結合で「存在確認」だけが目的（結合先の値そのものは使わない）なら、DISTINCTで重複排除するよりEXISTSで最初から重複を発生させない方がソートコストを回避できます。

### 集合演算はALLオプションで重複排除ソートを避ける

UNION・INTERSECT・EXCEPTは既定では重複排除のためのソートを行います。重複が発生しないことが分かっている、または重複を気にしなくてよい場合はUNION ALL等のALLオプションを使うとソートが発生しません。

| いつ使う | いつ使わない |
|---------|-------------|
| 集合が重複しないことが業務ロジック上保証できる | 重複排除そのものが目的の場合（ALL化すると結果が変わってしまう） |
| 大量データのソートコストを避けたい | DBMSがALLオプションを未実装・制限付きの場合（対象DBMS確認が必要） |

### WHERE句で書ける条件はHAVING句に書かない

```sql
-- 遅い: 全行を集約してからHAVINGでフィルタする
SELECT sale_date, SUM(quantity)
  FROM SalesHistory
 GROUP BY sale_date
HAVING sale_date = '2007-10-01';

-- 速い: 集約前にWHEREで絞り込む
SELECT sale_date, SUM(quantity)
  FROM SalesHistory
 WHERE sale_date = '2007-10-01'
 GROUP BY sale_date;
```

理由は2つあります。①GROUP BYの集約はソート/ハッシュ処理を伴うため、事前に行数を絞るほど負荷が下がる。②WHERE句側の条件ならインデックスが使える可能性があるが、集約後のビューは元テーブルのインデックスを引き継がないことが多い。GROUP化そのものに関わる条件（集約結果に対する条件）は当然HAVINGに残します。

### 集約よりも結合を先に行う

結合と集約を両方使うクエリでは、先に集約してから結合するより、先に結合してから集約する方が中間テーブルを省略できます。一対一・一対多の関係が保たれている結合では行数が水増しされないため、この順序変更は多くの場面で安全に適用できます。

### IN述語で複数キーを使う場合は一箇所にまとめる

```sql
-- 遅い: 同じ相関サブクエリを列ごとに繰り返す
SELECT id, state, city
  FROM Addresses1 A1
 WHERE state IN (SELECT state FROM Addresses2 A2 WHERE A1.id = A2.id)
   AND city  IN (SELECT city  FROM Addresses2 A2 WHERE A1.id = A2.id);

-- 速い: 行値式（row value expression）でまとめる
SELECT *
  FROM Addresses1 A1
 WHERE (id, state, city) IN (SELECT id, state, city FROM Addresses2 A2);
```

行値式をサポートするDBMSでは、複数のサブクエリを1回の非相関サブクエリに統合でき、検索回数も1回で済みます。行値式が使えないDBMSでは文字列連結で代用する方法もありますが、型変換の考慮が必要になるため行値式が使えるなら優先してください。

### サブクエリの一時テーブル化・ビューのネストを避ける

サブクエリの結果は新しいテーブルのように扱えますが、不用意に中間テーブルを重ねるとメモリ・ストレージを消費し、元テーブルに存在したインデックスを引き継げなくなります（特に集約を挟んだ場合）。

- 集約結果への条件はHAVINGで直接書き、わざわざ中間テーブルに落としてWHEREで絞らない（前述のパターン）。
- ビュー定義に集約関数（SUM/COUNT/AVG等）や集合演算（UNION等）が含まれる場合、そのビューを結合や集約と組み合わせるとパフォーマンスが劣化しやすい。複雑なビューを常用する場合、事前計算済みの構造（マテリアライズドビュー等）の採用は設計判断のため`lang:developing-databases`で検討する。
- ネストしたビュー（ビューを参照するビュー）は可読性は上がるが実行計画が読みにくくなり、オプティマイザが最適化しにくくなることがある。パフォーマンス問題の切り分け時は一度ネストを展開して実行計画を確認する。

### 相関サブクエリの除去

行ごとに比較対象の値（前月比・順位・累計等）を求める相関サブクエリは、多くの場合ウィンドウ関数で置き換えると高速化できます。相関サブクエリは行数分だけサブクエリが再実行されるのに対し、ウィンドウ関数は1回のソートで同等の結果を導けるためです。書き換えの具体例と判断基準は `WINDOW-FUNCTIONS.md` を参照してください。

### 極値関数（MAX/MIN）でインデックスを使う

```sql
-- テーブルの全件走査が必要
SELECT MAX(item) FROM Items;

-- 主キー等のインデックスが張られていれば、そのインデックスのスキャンだけで済む
SELECT MAX(item_no) FROM Items;
```

MAX/MINはソート自体をなくすわけではありませんが、対象列にインデックスがあればインデックスの端を読むだけで済み、実表への全件アクセスを回避できます。複合インデックスの場合も先頭列であれば同様に有効です。

## 判断基準総括表

| 技法 | 効果が出やすい状況 | 効果が出にくい／注意が必要な状況 |
|------|-------------------|--------------------------------|
| IN(サブクエリ)→EXISTS/JOIN | 結合キーにインデックスがある、大量データ | INの引数が固定値リストのみ |
| DISTINCT→EXISTS | 存在確認だけが目的の一対多結合 | 結合先の値自体を取得したい場合（代用不可） |
| UNION→UNION ALL | 重複が発生しないと保証できる | 重複排除そのものが要件の場合 |
| WHERE先出し | 集約前に絞り込める条件がある | 集約結果自体に対する条件（本来HAVING向き） |
| 集約より結合を先に | 一対一・一対多の結合 | 多対多の関係（正規化設計を要確認） |
| SARGable書き換え | 索引列に演算・関数・型変換が付いている | 元々選択率が高くインデックス自体が不向きな列 |
| 相関サブクエリ除去 | 行間比較・順位・累計を相関サブクエリで書いている | 単純な存在確認（EXISTSの方が素直） |

---

## developing-databases への委譲判断（AskUserQuestion）

### 確認不要（一義的に決まる）

- 索引列の左辺で演算・関数を使わない、型変換は条件値側で行う、否定形より肯定形を優先する、といったSARGable化の原則は確認不要でそのまま提示してよい。
- IN(サブクエリ)をEXISTS/JOINへ書き換える定石も、NULL混入によるNOT IN/NOT EXISTSの非同値（FOUNDATIONS-AND-NULL.md参照）を踏まえていれば確認不要。

### 確認が必要（AskUserQuestion必須）

クエリの書き換えだけでは目標のパフォーマンスに届かず、次のようなスキーマ側の変更に踏み込む必要がある場合は、推測で進めず必ず確認する。

```markdown
### ユーザー確認の原則（AskUserQuestion）

判断分岐がある場合、推測で進めず必ずAskUserQuestionツールでユーザーに確認する。

確認すべき場面:
- クエリの書き換えだけでは改善が見込めず、インデックスの追加・変更が必要な場合
- 非正規化やマテリアライズドビュー導入など、スキーマ・データモデルの変更に及ぶ場合
- パーティショニングやデータマート等、物理設計レベルの対処が候補に挙がる場合

確認不要な場面:
- SARGable条件への書き換えなど、クエリテキストの変更だけで完結する場合
- 明確に一義的な定石（IN→EXISTS等、NULL安全性を確認済みのもの）を適用する場合
```
