## [LRN-20260731-002] best_practice

**記録日時**: 2026-07-31T09:20:00+09:00
**優先度**: medium
**ステータス**: pending
**領域**: EPUB画像ベースコンテンツのOCR変換

### 要約
固定レイアウト（fixed-layout）画像ベースEPUBをOCR変換する際、画像ファイル名（`image_rsrcXXXX.jpg`
形式）は読み順と無関係のハッシュ名で、spine順（`content.opf`の`itemref`順）と直接対応しない。
xhtml⇄画像の対応を自前でパースするより、`pandoc -t markdown`で変換した際に画像参照が出現する順
（pandocがspine順にxhtmlを処理する副産物）を抽出し、その順で画像を`0001.jpg`形式にリネームコピー
してから`ocr-apple-vision`等の画像ディレクトリ入力のOCRツールに渡すのが簡便で確実だった。

### 手順
```bash
pandoc -t markdown -o /tmp/check.md book.epub
python3 -c "import re; ... re.finditer(r'image_rsrc[A-Za-z0-9]*\.(?:jpg|jpeg|png)', text) ..."
# 出現順（重複除去）でリネームコピー → OCRツールへ
```

### 教訓
EPUBのページ順が必要な場面では、xhtml解析を自作せず「pandocの処理順」という既存ツールの副産物を
再利用する方が実装コストが低い。

**Recurrence-Count**: 1（初出）

## [LRN-20260730-001] best_practice

**記録日時**: 2026-07-30T14:45:00+09:00
**優先度**: medium
**ステータス**: pending
**領域**: creating-flashcards / OCR

### 要約
見開き型「問題ページ＋座標マッチングで判定マーカーを紐付ける」OCRパイプライン（座標系Apple Vision抽出）で、
判定マーカー欠落率26.5%（1682件中446件）の原因を調査したところ、単一の欠陥ではなく独立した11件の
不具合が積み重なっていた。1件ずつ潰した結果、欠落率は26.5%→0.05%（1988件中1件）まで改善し、
その最後の1件も原本画像を直接目視して手動で正解を確定・投入した（**最終的に1988件全件を解決**）。

### 詳細
「ケータイ弁理士」EPUBの一問一答形式（`practice_page_extract.py`: 本文列を`口`(U+53E3)始まりの行で
新設問と判定→y座標最近傍でマージン列の`○/✕`マーカーと紐付け）で判明した原因11件:

1. **チェックボックス記号「□」の誤認識ゆらぎ**: Apple Visionが同一書籍内で「口」(1285件)以外に
   「■」(149件)・「ロ」片仮名(49件)・「コ」片仮名(6件)にも誤認識していた。新設問の判定が`[口□]`
   の2文字しか見ていなかったため、■/ロ/コで化けた設問はサイレントに前の設問へ結合され、以降の
   y座標マッチングが連鎖的にずれていた（`is_new_q`正規表現を`[口□■ロコ]`へ拡張して解消）。
2. **マージン列のVision検出漏れ**: ページ全体1回のOCRパスでは、印刷上は明瞭に存在するマーカー
   テキスト領域そのものをVisionが返さないことがある（誤読ではなく検出漏れ）。マージン列だけを
   切り出して2倍拡大＋別OCRパスにすると多くを回収できた。
3. **丸囲み数字の副番号形式**: 「（1）①答○」「（1）②答×」のように1つの外側番号に複数の丸数字
   副番号が束ねられる書式があり、既存正規表現が「丸囲み数字も含め必ず閉じ括弧が要る」前提だった
   ため丸囲み数字（括弧なしで自己完結する記号）を一切拾えていなかった。数字トークンと丸囲み
   トークンを別ルールに分離（丸囲みは括弧不要）して解消。
4. **マージン検出漏れの回復率は拡大率自体が非決定的**: 同一マーカーが2倍拡大では拾えず3倍拡大
   では拾える（またはその逆）ケースがあった。2倍・3倍の両方でOCRし結果を合算（重複は無害・
   各設問はy最近傍の未使用マーカー1件のみ消費）することで安定した。
5. **メイン列（設問文）でも同じVision検出漏れが起きる**: 4行ある設問の2〜4行目が丸ごと検出されず
   文が「。」に到達せず途中で切れるケースがあった。②と同じ切り出し＋拡大で対処するが、
   🔴 **2倍・3倍の結果を単純に合算するのは危険**（既存パイプラインのマージン列と違い、メイン列は
   複数行を1設問に結合するため、拡大率ごとに異なる行分割結果を混ぜると同じ内容が微妙に違う文字列
   として重複挿入され設問がめちゃくちゃに分裂する＝実機で21問誤検出を確認）。正しい対処は
   「元の1回・2倍・3倍それぞれを独立した完全な再構成としてパースし、末尾が『。』で終わる設問が
   最も多い（＝最も欠落が少ない）版を丸ごと採用」——部分マージではなく全置換で選ぶ。
6. **チェックボックス文字クラス拡張の副作用（イ・ロ・ハ表記との衝突）**: ①で追加した「ロ」「コ」は、
   日本語法律文の一般的な事例ラベル表記（甲乙丙と同様に「発明イ」「発明ロ」「発明ハ」等で使う）
   とも一致するため、行の折り返し位置がたまたま「ロ」で始まると正当な続き文まで新設問と誤判定
   していた（実機1件確認）。文字だけでは判別不能——**チェックボックス行は常に本文の折返し行より
   浅い左端x座標**（本書は約0.127 vs 約0.16+）にあるため、ページごとに実測した「チェックボックス
   候補行の最小x値」を基準に、そこから離れた（+0.02超）ロ/コ始まりは無視するようx座標ガードを
   追加して解消。この自己校正方式は元のフルページ座標系にも②④の切り出し後の再スケール座標系にも
   そのまま使える（絶対座標のハードコードは不可）。
7. **複数参照番号マーカーの閉じ括弧欠落**: 「（2）（3）答〇」のように2つの参照番号が連結される
   マーカーで、2つ目の番号の閉じ括弧が「答」の直前で欠落する誤読（「（2）（3答〇」）が発生。
   さらに拡大率次第でこの誤読パターンすら変化する（等倍クロップでは「答」を含めて読めるのに、
   2倍・3倍拡大では「答」の文字ごと消えて別の誤読になる逆転現象を実機確認）。開き括弧だけでなく
   **閉じ括弧も省略可能**に緩和し、マージン列の拡大候補に**等倍（クロップのみ・拡大なし）も追加**
   して2/3倍との和集合を取ることで解消。
8. **チェックボックスの誤認識先はさらに稀少パターンもある**: 「0」（数字ゼロ）・「◎」・半角「o」
   への誤読も1件ずつ実機確認。当初は出現数が少なく本文中の誤爆リスクを懸念して除外していたが、
   ⑥のx座標ガードを先に導入したことで「文字だけで判定しない」防御が既に効いているため、これらを
   文字クラスに追加しても安全（誤爆はx座標ガードが弾く）と判断し追加。1件のみの出現でも見逃すと
   隣接設問ごと丸ごと結合・文章破損（句点未到達の途中切れ）を招くため、出現数の多寡だけで
   採否判断しないこと。
9. **丸囲み"ラテン文字"は実在せず別記号に化ける**: 「（4）③Ⓒ答×」のように丸数字のさらに下位に
   丸囲みラテン文字（Ⓐ Ⓑ Ⓒ...）を使う3階層参照形式があったが、Apple Visionは本物のUnicode
   circled-letter文字を一切出力しない。視覚的に似た別記号（「◎」拡大率1〜2倍時／「©」3倍時）に
   置き換えて出力し、しかも同一の元記号なのに拡大率で置換先が変わる（③④と同型の非決定性）。
   本物のCircled Letter Unicode範囲を文字クラスに加えても無意味——実際に観測された代替記号
   （◎・©）そのものを許容トークンとして追加する必要がある。
10. **ページ番号フッターの文字化けが最終行を汚染**: 「・111・」のようなページ末尾の丁数フッターが、
    数字ではなく「・_-_・」のようなアンダースコア記号列に誤読されることがあった。既存フッター除外
    正規表現は数字前提だったためすり抜け、最後の設問の続き行として誤結合→y座標が0.06超ずれて
    判定マーカーが完全に迷子になった。対策は正規表現の精緻化ではなく**位置ベースの一般化**（ページ
    最下部y<0.055かつ短い行は中身を問わず除外）。あわせて、閉じ括弧「］」自体が誤読で消えて出典が
    取れないケース（「［H26-49］」→「［H26-491」）向けに、文末まで続く未閉じ括弧を出典として
    救済するフォールバックも追加。
11. **「答」の文字自体も誤読される／括弧パターンの過剰な作り分けは統合すべき**: 「答」（かい，
    「回答」の意）が視覚的に似た「容」に誤読される実例（「は（9）容✕」）を確認し、「答」の位置を
    `[答容]`に緩和。さらに、③④⑦⑧で個別対応していた「括弧あり数字」「括弧なし丸数字」「括弧あり
    丸数字（例:「（⑧）」）」という3つの別パターンを、実は「開き括弧・閉じ括弧はどちらも常に省略可、
    トークン種別（数字/丸数字/代替記号）とは独立」という**1つの統一ルール**に単純化できることが
    判明（`_NUM_GROUP`を1本の正規表現に統合）。個別パターンを次々継ぎ足すより、根底にある「括弧の
    有無はトークン種別と無関係に常に非決定的」という構造に早く気づいて統一した方が、コードも
    シンプルになり見落としも減る。
12. **最後の1件は真のOCR限界**: 上記全修正後も1件だけ、拡大率を1〜6倍まで総当たりしてもVisionが
    マーカー領域を一切検出しなかった（誤読ではなく完全な無反応）。原本画像を直接目視して正解
    （verdict・出典・対応する基礎知識ページの項目文）を人力で確定し、`qapairs.json`を直接編集して
    解消。**自動化には原理的な天井がある**——コードで追えるのは「非決定的だが何らかの形で検出は
    される」パターンまでで、Visionが本当に何も返さないケースは目視確認・手動投入以外に解がない。

改善の推移: 446件失敗(26.5%, 1682件中) → ①適用後526件(1995件中26.4%、合流していた設問が独立し
総数が増えたが未解決率はほぼ変わらず) → ②適用後321件(16.1%) → ③適用後119件(6.0%) → ④適用後
32件(1.6%) → ⑤⑥適用後24件(1986件中1.2%) → ⑦⑧適用後7件(1988件中0.35%) → ⑨⑩⑪適用後1件
(0.05%) → ⑫手動確定で**0件（全1988件解決）**。

### 推奨アクション
座標系Apple Vision抽出を新しい書籍に適用する際は、上記12パターンを事前チェックリストとして参照する
（`practice_page_extract.py`相当のスクリプトを書く際、新設問判定文字クラス＋x座標ガード・メイン列/
マージン列共通の複数スケールOCR（1x/2x/3x、メイン列は「合算ではなく全置換で最良版選択」・マージン列は
「和集合で合算可」）・丸囲み数字/代替記号許容・**括弧の開閉は常に両方省略可能という統一ルール**（数字/
丸数字/代替記号のトークン種別で場合分けしない）・「答」の視覚的誤読許容・ページ最下部の位置ベース
フッター除外・未閉じ引用括弧の救済フォールバック、を最初から組み込む）。汎用化するなら
`creating-flashcards`の`references/CONTENT-BY-TYPE.md`または`OCR-CONVERSION.md`に「座標マッチング
方式の既知の罠」として恒久化する候補（本件はプロトタイプスクリプトでの発見のため、スキル本体への
反映は要判断）。なお設問文頭のチェックボックス記号自体（口/■/ロ/コ/0/◎/o）は内容として無意味な
ため、投入前に`statement[0] in "口□■ロコ0◎o"`で除去すること。**教訓**: 「あと数件だから損益分岐点」
と早めに見切りをつけたくなるが、実際には個別バグに見えた残存ケースの多くが③④⑥と同型の既知パターン
（括弧の非決定性・拡大率依存の誤読ゆらぎ・稀少誤認識先）の再発だった。真に一点物（本件では拡大率
総当たりでも無反応の1件のみ）に到達するまで掘り下げる価値があった。
